大尉，我看完你上传的 Codex Chrome 插件包后，结论是：**Codex 的 Chrome tab group 不是直接绑定 `sessionId`，而是绑定在一套 tab lease 生命周期上。`session_id` 是所有权根 ID，`turn_id` 是本轮操作 ID，`tabId` 是资源实体，`groupId` 只是 UI 展示容器。**

从插件源码看，Codex 和你们现在 Formax 最大的差别是：**Codex 插件不会在缺少 `session_id` 时自己随机生成一个 session；它直接报错。** 也就是说，稳定的 session 必须由上游 Codex app / native host / browser client 传进来。

源码里有这个逻辑：

```ts
requireSessionId(params) {
  const sessionId = params?.session_id;
  if (typeof sessionId !== "string") {
    throw new Error("Missing required browser session_id");
  }
  return sessionId;
}

requireTurnId(params) {
  const turnId = params?.turn_id;
  if (typeof turnId !== "string") {
    throw new Error("Missing required browser turn_id");
  }
  return turnId;
}
```

所以 Codex 不是：

```text
没有 sessionId -> extension 随机生成 -> 新 group
```

而是：

```text
没有 session_id -> 命令失败
```

这点和你们现在 `resolveNewSessionId()` 随机 UUID 的行为差异非常大。

## 1. Codex 这几个 ID 的层级关系

源码里真正相关的 ID 可以分成这几层：

| ID                          | 来源                                       | 生命周期                      | 作用                                     | 是否直接决定分组          |
| --------------------------- | ---------------------------------------- | ------------------------- | -------------------------------------- | ----------------- |
| `extensionId`               | `chrome.runtime.id`                      | 插件安装后固定                   | 标识 Chrome extension                    | 否                 |
| `extensionInstanceId`       | 插件 `onInstalled` 时 `crypto.randomUUID()` | 存在 `chrome.storage.local` | 标识当前插件实例，写进 tab lease                  | 否                 |
| `session_id` / `sessionId`  | 上游 Codex 传入                              | 跨多个 turn 稳定               | browser session 的根所有权 ID               | 间接决定              |
| `turn_id` / `turnId`        | 上游 Codex 每轮传入                            | 通常每轮 agent turn 变化        | 标识当前回合，用于清理、cursor、lease 更新            | 否                 |
| `tabId`                     | Chrome `chrome.tabs.*` 返回                | Chrome tab 生命周期           | 真正被控制的 tab 资源                          | 是 lease key       |
| `origin`                    | Codex 内部写入：`agent` / `user`              | 随 tab lease               | 区分 agent 创建的 tab 和用户 claim 的 tab       | 影响关闭/保留策略         |
| `lease.state`               | Codex 内部：`active` / `handoff`            | 随 turn/finalize 改变        | 判断 tab 当前是否被控制、是否交接到下轮                 | 强影响复用             |
| `chromeGroupId` / `groupId` | `chrome.tabs.group()` 返回                 | Chrome tab group 生命周期     | UI 上的标签分组                              | 只是容器，不是根 ID       |
| `browser_id`                | bundle 里 capability command schema 使用    | 更高层 SDK/transport 概念      | 用于 page assets / webmcp / viewport 等命令 | 不参与核心 group lease |
| JSON-RPC `id`               | transport 自增                             | 单个请求-响应                   | 匹配 native message 响应                   | 否                 |
| `moveSequence`              | extension 自增                             | 单次 cursor movement        | 等待鼠标动画到达                               | 否                 |

核心关系是：

```text
Codex app / native host
  ├─ session_id：稳定 browser session
  └─ turn_id：当前 agent turn

Chrome extension
  └─ sessions[session_id]
       ├─ currentTurnId = turn_id
       ├─ activeTabId = 逻辑活动 tab
       └─ TAB_LEASES[tabId]
            ├─ sessionId
            ├─ turnId
            ├─ origin: "agent" | "user"
            ├─ state: "active" | "handoff"
            ├─ instanceId
            └─ groupId? 仅 handoff 时可能保存

TAB_GROUPS
  └─ chromeGroupId
       ├─ title
       ├─ presentationColor
       └─ managed group metadata
```

一句话：**`session_id` 拥有 tab lease，tab lease 决定哪些 tab 属于这个 session，tab 所在的 Chrome group 决定 UI 分组。**

## 2. Codex 什么时候创建新 group？

Codex 不是在 `startSession` 时创建 group，而是在 `createTab` 时创建或复用 group。

源码流程大概是：

```ts
createTab(turnId) {
  const existingAgentTabs = await activeAgentTabIds();

  const tab = await createChromeTab();

  await tabGroups.ensureAgentTabGroup(
    sessionId,
    tab.id,
    existingAgentTabs
  );

  await tabLeases.claimTab(
    sessionId,
    turnId,
    tab.id,
    "agent"
  );
}
```

关键函数是 `ensureAgentTabGroup(sessionId, newTabId, activeAgentTabIds)`：

```ts
const group = await findManagedGroupContainingTabs(activeAgentTabIds);

if (group) {
  syncSessionTitle(group, sessionId);
  await addTabToGroup(group, newTabId);
  await reconcileGroupPresentation(group.chromeGroupId);
  return group;
}

const newGroup = await createGroup(
  newTabId,
  sessionGroupTitles.get(sessionId)
);
```

所以 Codex 创建新 group 的条件是：

```text
createTab 被调用
  └─ 当前 session 下没有任何 active agent tab 位于已有 managed group
       └─ 创建新的 Chrome tab group
```

Codex 复用旧 group 的条件是：

```text
createTab 被调用
  └─ 当前 session 下已有 active agent tab
       └─ 这个 tab 还在 Codex 管理的 Chrome group 里
            └─ 新 tab 加入这个旧 group
```

注意这里很关键：**Codex 不是用 `sessionId -> groupId` 的固定映射来找 group。**
它是通过当前 session 拥有的 agent tabs，反查这些 tab 所在的 Chrome group。

也就是说，真实关系更像这样：

```text
session_id
  -> active/handoff tab leases
      -> tabId
          -> chrome.tabs.get(tabId).groupId
              -> TAB_GROUPS metadata
```

而不是：

```text
session_id -> groupId
```

## 3. `TAB_LEASES` 是 Codex 的核心，group 只是 UI

Codex 有一个持久化的 lease store，key 是 `TAB_LEASES`，存在 `chrome.storage.session`。

每个 lease 结构大概是：

```ts
{
  tabId,
  sessionId,
  turnId,
  origin: "agent" | "user",
  claimedAt,
  instanceId,
  state: "active" | "handoff",
  groupId?,
  isActiveHandoff?
}
```

`claimTab(sessionId, turnId, tabId, origin)` 的行为是：

```ts
if tab 已经 active:
  if tab.sessionId !== 当前 sessionId:
    throw Error("Tab is already part of browser session ...")

  如果是同一个 session:
    更新 turnId / instanceId

else:
  新建 active lease
```

所以一个 tab 在 Codex 里不能同时属于两个 browser session。
这点和单纯用 group 包 tab 不一样：**Chrome group 是 UI，lease 才是 ownership。**

---

## 4. `turn_id` 的作用：不是分组，而是回合边界

`turn_id` 不决定 Chrome group。它主要负责：

1. 标记当前操作属于哪一轮 agent turn。
2. 更新 active leases 的 `turnId`。
3. cursor overlay 使用 `sessionId:turnId:moveSequence` 识别鼠标动画。
4. `turnEnded` 时释放当前 turn 的 active leases。

源码里 `turnEnded` 会做类似这个事情：

```ts
endTurn(turnId) {
  if currentTurnId !== turnId return;

  detach debuggers;
  stop session overlay;
  releaseActiveTurn(sessionId, turnId);
  activeTabId = null;
  currentTurnId = null;
}
```

所以跨 turn 复用 tab/group 的关键不是 `turn_id` 不变，而是 **finalize 阶段有没有把 tab 标成 `handoff`**。

---

## 5. `handoff` 是 Codex 跨 turn 复用 group 的关键

Codex 有一个很重要的生命周期函数：`finalizeTabs(turnId, keep)`。

它把 tabs 分成几类：

```text
keep status = "handoff"
  -> lease 从 active 变成 handoff
  -> 保存 groupId
  -> 下一轮同 session_id 可以 resume

keep status = "deliverable"
  -> 从 managed group 里移出
  -> release lease
  -> tab 还留给用户看
  -> favicon 打 deliverable badge

agent 创建但没 keep
  -> 关闭 tab

user claim 但没 keep
  -> release lease
  -> 不关闭用户 tab
```

相关逻辑：

```ts
if status === "handoff":
  tabLeases.handoffTabs(sessionId, turnId, tabIds, { groupId, activeTabId })

if status === "deliverable":
  tabGroups.releaseTabsFromManagedGroups(tabIds)
  tabLeases.releaseTabs(sessionId, tabIds)

if origin === "agent" and not kept:
  chrome.tabs.remove(tabIds)
```

下一轮开始时：

```ts
resumeHandoffIfPresent(newTurnId) {
  const handoffLeases = getSessionHandoffLeases(sessionId);

  resumeHandoffTabs(sessionId, newTurnId, tabIds);

  if groupId exists:
    reconcileManagedGroupForTabs(sessionId, groupId, tabIds);

  activeTabId = previousActiveHandoffTab ?? firstTab;
}
```

这说明：**Codex 跨 turn 复用旧 group，靠的是 handoff lease，而不是简单地“同一个 sessionId 就永远一个 group”。**

更准确地说：

```text
同一个 session_id
  + 上一轮有 handoff tabs
  + handoff tabs 还存在
  + handoff tabs 的 group 还存在
= 下一轮复用旧 group
```

如果上一轮没有 handoff，或者 active leases 在 `turnEnded` 时被释放了，那么即使 `session_id` 相同，下一次 `createTab` 也可能创建新 group。

## 6. `TAB_GROUPS` 里存的不是 session -> group

Codex 的 `TAB_GROUPS` 存在 `chrome.storage.local`，结构大概是：

```ts
{
  groups: [
    {
      chromeGroupId,
      presentationColor,
      title
    }
  ],
  sessionGroupTitles: {
    [sessionId]: title
  }
}
```

重点：`groups` 里没有直接保存 `sessionId`。

它只保存：

```text
chromeGroupId -> title/color metadata
sessionId -> title
```

也就是说，Codex 没有一个强绑定表：

```text
sessionId -> chromeGroupId
```

它是通过 tab lease 和 tab 当前所在 group 来恢复关系的：

```text
sessionId
  -> active/handoff leases
      -> tabIds
          -> tabs.get(tabId).groupId
              -> groupMetadata
```

这比 Formax 现在的 “sessionId 直接对应 group” 更松耦合，也更适合处理 tab 被用户移动、service worker 重启、turn 结束、deliverable/handoff 等情况。

---

## 7. Codex group 的标题也不是 sessionId

Codex 默认 group 标题是：

```ts
defaultSessionGroupTitle = "Codex";
```

`nameSession(sessionId, name)` 只会设置一个用户可读标题：

```ts
sessionGroupTitles.set(sessionId, title)
```

然后 group presentation 会把 Chrome group title 改成：

```text
title ?? "Codex"
```

这和你们现在的：

```text
Agent ${sessionId.slice(0, 6)}
```

差异很大。

所以 Codex 即使内部有多个 session/group，视觉上也不一定像你们这样暴露一堆 `Agent abc123`。你们现在把随机 sessionId 暴露到 group title 上，会让“session 频繁重建”的问题特别明显。

## 8. 和你们当前 Formax 的关键差别

根据你贴出来的 Formax 逻辑，你们现在更像：

```text
browser-client / extension 收到命令
  -> 如果没有 sessionId
       -> resolveNewSessionId()
       -> 随机 UUID
       -> 创建 group: Agent xxxxxx
  -> 后续只有继续带同一个 sessionId 才复用 group
```

Codex 更像：

```text
上游必须传 session_id / turn_id
  -> extension 不兜底生成 session_id
  -> session_id 找到 per-session controller
  -> tab lease 记录 tab 归属
  -> createTab 时通过现有 agent tab 反查 managed group
  -> finalizeTabs 决定 deliverable / handoff / close / release
  -> 下一轮通过 handoff lease 恢复 group
```

所以你们“容易生成很多分组”的根因不只是 group manager 写法，而是整个 ID 模型少了一层：

```text
stable browser session id
  + per-turn id
  + tab lease
  + handoff/finalize lifecycle
```

现在你们更像：

```text
sessionId 丢了 -> 新 UUID -> 新 group
```

Codex 是：

```text
session_id 丢了 -> 命令失败，不会悄悄新建 group
```

这个差异非常关键。

## 9. 新开一个对话到底该不该新 group？

从 Codex 插件源码本身看，答案是：**插件不决定“新对话是否新 group”，上游传入的 `session_id` 决定。**

也就是说：

```text
新对话，但上游继续传同一个 session_id
  -> Codex extension 认为还是同一个 browser session
  -> 有 handoff/active agent tabs 时复用旧 group

新对话，上游传新的 session_id
  -> Codex extension 认为是新的 browser session
  -> createTab 时大概率新 group
```

所以“Codex 看起来总在一个 group”可能有三个原因：

1. Codex 上游在同一个 thread/run 内持续传同一个 `session_id`。
2. Codex 把上一轮 tab 标成了 `handoff`，下一轮 resume。
3. Codex group 标题默认都是 `"Codex"`，不像你们把随机 sessionId 显示出来，所以多个 group 不那么刺眼。

插件侧无法证明 `session_id` 是不是绑定 Codex thread，因为这个 zip 里没有完整 Codex app/native host 的生成逻辑。但 extension 侧可以确定：**它只消费 `session_id`，不生成它。**

## 10. 我建议你们按这个模型改

你们可以把 ID 模型改成这样：

```text
conversationId / runId
  -> browserSessionId
      -> turnId
          -> tab leases
              -> tabId
                  -> chromeGroupId
```

具体落地：

```ts
type TabLease = {
  tabId: number;
  sessionId: string;
  turnId: string;
  origin: "agent" | "user";
  state: "active" | "handoff";
  claimedAt: number;
  instanceId: string | null;
  groupId?: number;
  isActiveHandoff?: boolean;
};
```

然后规则改成：

```text
1. extension 不要在缺 sessionId 时随机生成。
   缺 sessionId 要么报错，要么显式 reuseLatestSession，不要悄悄新建。

2. browser-client 默认注入 stable sessionId。
   可以来自 FORMAX_BROWSER_SESSION_ID、当前 chat id、agent run id、workspace id。

3. turnId 每轮变化。
   turnId 不参与 group 命名，不参与 group 创建，只用于清理和 handoff。

4. tab ownership 存到 TAB_LEASES。
   key 是 tabId，value 是 { sessionId, turnId, origin, state }。

5. group 不直接绑定 sessionId。
   createTab 时先找当前 session 的 active/handoff agent tabs，再从这些 tabs 反查已有 managed group。

6. 增加 finalizeTabs。
   deliverable：释放 lease、移出 managed group、保留 tab。
   handoff：保留 lease、保存 groupId、下轮 resume。
   agent temporary：关闭。
   user claimed：释放但不关闭。

7. group title 不要用 sessionId slice。
   默认叫 "Formax" 或任务名；否则随机 session 抖动会直接暴露到 UI。
```

最终你们应该从现在的：

```text
sessionId -> group
```

升级成：

```text
sessionId -> leases -> tabs -> group
```

这就是 Codex 这套设计里最核心的区别。
